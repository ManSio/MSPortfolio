## 1. Контекст (зачем это вообще)

`verify_claim` v1 — детерминированный evidence score: claim разбивается на токены
(≥4 символа, минус стоп-слова), ищем ≥2 совпавших токена **в одной записи** корпуса.
Precision-first: никогда не выдаём ложное `supported` — лучше честный отказ.

**Ограничение (KI-017):** recall ограничен буквальным совпадением слов. Перефразировка
«занимается векторным поиском и ранжированием» не найдёт запись про «LanceDB/BM25 hybrid
search», хотя утверждение правдиво. Однословные утверждения всегда отказываются.

**Цель v2:** поднять recall для синонимов/перефразировок, **не снижая** precision-гарантию v1.

## 2. Не-цели (осознанные отказы)

- ❌ LLM НЕ пишет и НЕ редактирует корпус (circular-logic риск: «verified, потому что LLM сказал»).
- ❌ LLM-скоринг как *замена* детерминированной руки в hot-path (флаки, стоимость, латентность).
- ❌ Полный semantic search поверх эмбеддингов всего корпуса (это отдельный проект, не «рука»).

## 3. Дизайн-варианты

### Вариант A — LLM как «второе мнение» при промахе детерминированной руки (рекомендуется)
- **Как работает:** 1) детерминированная рука v1 без изменений; 2) если `supported: false` —
  LLM получает claim + топ-K кандидатов из корпуса (по токенному пересечению, K=5) и отвечает
  строго да/нет + цитата записи; 3) вердикт LLM **дополняет**, но не отменяет детерминированный.
- **Плюсы:** детерминированный `supported: true` никогда не понижается (precision-флоор сохранён);
  recall-прирост там, где он реально нужен (перефразировки); корпус не расширяется.
- **Минусы:** стоимость/латентность только на промахах (~доля запросов); LLM может ошибаться
  в другую сторону (false-acceptance) — нужен guard (см. §5).

### Вариант B — эмбеддинг-подобие (без LLM)
- **Как работает:** предвычисленные векторы записей корпуса; claim → эмбеддинг → top-K по cosine.
- **Плюсы:** дёшево после индексации, детерминированно-воспроизводимо, без стоимости за вызов.
- **Минусы:** подбирает *похожее*, а не *подтверждает* — высокий false-acceptance на близких по
  теме, но разных фактах («работал с Python» vs «проект на Python» — не одно и то же);
  выбор embedder = новый пин зависимости (§5.19 AGENTS.md).

### Вариант C — синонимическое/стемминг-расширение токенов (детерминированное)
- **Как работает:** словарь синонимов/стемминг перед матчингом.
- **Плюсы:** ноль стоимости, детерминизм.
- **Минусы:** ограниченный прирост; ручной словарь — техдолг; не решает структурные
  перефразировки (порядок слов, обобщения).

## 4. Рекомендация

**A, поэтапно:**
1. **Этап 0 (eval-first, CI):** парафраз-набор тестов (см. §6) — зафиксировать baseline recall v1.
2. **Этап 1 (офлайн-оценка):** LLM-рука как отдельная функция `verifyClaimLlmArm()` — прогнать
   парафраз-набор, измерить recall-прирост и false-acceptance. Критерий входа в hot-path:
   false-acceptance ≤ 1% на контроле (негативные claim'ы, включая «работал в Google/Meta»).
3. **Этап 2 (в туле, с флагом):** в `verify_claim` — если детерминированно `false` → опциональный
   LLM-вызов с guard (§5). LLM-результат помечается (`arm: 'llm'`), чтобы потребитель видел
   источник вердикта. Пока LLM недоступен/таймаут — вердикт как у v1 (fail-closed).
4. **Этап 3 (видимость):** evidence-фрейм на сайте и виджет ClaimVerifier показывают `arm`
   (deterministic/llm) — «панель доказательств» остаётся честной про происхождение вердикта.

## 5. Precision-guard (обязателен, до любого кода)

- LLM-рука вызывается **только** на детерминированном промахе; `supported: true` от v1
  не пересматривается.
- LLM обязан вернуть **идентификатор записи корпуса** (source path), а не только «да».
  Нет цитаты → отказ (fail-closed).
- Прогрев модели — с фиксированной температурой 0 и жёстким системным промптом
  («verify against THIS corpus, answer only supported/refused, never infer beyond the text»).
- Каждый LLM-вердикт логируется в eval-сетах; метрика false-retraction/acceptance — в CI
  (dual-arm: negative control обязан падать при введённом дефекте).

## 6. Eval-набор (расширение evidence-eval.test.ts)

- **Парафраз-набор:** для каждого из ~15 канонических claim'ов реестра — 2-3 перефразировки
  (синонимы, перестановка слов, обобщение). Пример: «LanceDB and BM25 hybrid search» →
  «комбинирует векторный поиск с BM25-ранжированием» (эта перефразировка сейчас НЕ
  матчится — фиксирует текущий recall-гэп).
- **Метрики:** recall@supported на парафразах (цель: ≥80% против ~40-50% у v1), precision
  (подтверждённые среди всех supported — цель 100%), false-acceptance на негативных контролях
  (цель ≤1%), латентность p95 LLM-руки (бюджет: <3 c на запрос).
- **Негативные контроли остаются жёсткими:** «worked at Google», «led a team at Meta» —
  обязаны остаться `refused` и в LLM-руке.

## 7. Стоимость / риски

| Риск | Митигация |
|------|-----------|
| Стоимость LLM-вызовов | Только на промахах (меньшинство запросов); кэш вердиктов по хэшу claim; лимит на IP уже есть (KV-квота D4) |
| Латентность | Асинхронная рука с таймаутом; сайт — не блокировать рендер |
| Флаки (разные вердикты между прогонами) | t=0, жёсткий промпт, повторяемость в eval; LLM-вердикт помечается как `llm`, не выдаётся за факт |
| Circular logic | LLM никогда не пишет в корпус; вердикт привязан к source-пути записи |
| Зависимость (модель/провайдер) | Через существующую OpenRouter-цепочку из /chat; провайдер — конфиг, не хардкод |

## 8. Concurrency

`verify_claim` stateless: корпус строится один раз при импорте (EVIDENCE_CORPUS), LLM-вызов —
локальный для запроса (fetch), без общего мутабельного состояния. Два одновременных вызова
не пересекаются; кэш вердиктов — KV/модульный Map с TTL, без гонок на запись-в-запись
(кто первый записал — тот и прав, идемпотентно по хэшу). Стресс-тест на корректность
(правильный claim → правильный вердикт) при реализации — N=2 и N=8 (§5.13 AGENTS.md).

## 9. Definition of Done

1. Парафраз-набор в `tests/evidence-eval.test.ts`, baseline v1 зафиксирован.
2. `verifyClaimLlmArm()` реализована и прогнана офлайн: recall ≥80%, false-acceptance ≤1%.
3. Guard'ы §5 реализованы и покрыты тестами (включая negative controls и недоступный LLM → fail-closed).
4. `arm: 'deterministic' | 'llm'` в результате тула + видимость в evidence-фрейме сайта.
5. Числа (recall/precision/latency) — с командой замера в EXPERIMENTS_LOG.md (§5.15 AGENTS.md).
6. KI-017 закрыт с пометкой «v2 реализован» (или переоткрыт с остаточным гэпом).
