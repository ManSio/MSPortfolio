# MCP-сервер: заметки по безопасности (аудит, 2026-08-14)

> **Источник:** текст вставлен владельцем из анализа, подготовленного другим агентом.
> **Статус проверки (⚠️):** статистика и CVE в этом файле **не верифицированы независимо**
> (у нас нет сетевого доступа в песочнице). Они помечены как «со слов источника» и не
> должны подаваться как проверенные факты без отдельной проверки.
> **Сверка с кодом репозитория** — в разделе «Проверено по коду» внизу.

## Ограничение честно

У меня нет полноценного браузера с рендерингом JS и нет сетевого доступа из песочницы
(bash без интернета), а `web_fetch` работает только по URL, которые уже засветились в
поиске/предыдущих фетчах. Так что настоящий пентест (сканирование портов, проверка
заголовков, XSS-инъекции, CORS-тесты и т.д.) я запустить не могу — это будет имитация,
а не реальный результат. Зато я могу:

1. дать чек-лист, что проверить самому (это и есть "red team" в применимом виде для
   статичного GitHub Pages сайта);
2. поресёрчить реальные тренды и уязвимости именно в контексте MCP-серверов и
   агентских сайтов 2025-2026.

## Почему это релевантно именно твоему сайту

У тебя MCP-сервер публично торчит наружу и отвечает агентам. Это ровно тот класс
систем, который сейчас массово атакуют. Свежая статистика по проверенным MCP-серверам
показывает, что 43% протестированных серверов уязвимы к командной инъекции, а 82%
операций с файлами в 2614 реализациях подвержены path traversal, и отдельно SSRF
встречается у 36.7% из более чем 7000 серверов. Это не теория — за этим стоят реальные
CVE, включая уязвимость в mcp-remote с CVSS 9.6, дающую полноценный RCE на машине
клиента при подключении к недоверенному удалённому MCP-серверу.

## Конкретные векторы, которые стоит закрыть у себя

1. **Что именно отдаёт твой MCP-сервер.** Если он не только читает (метрики, decision
   log), но и что-то исполняет — это критично. Даже официальный Git MCP-сервер
   Anthropic ловил цепочку из path traversal, argument injection и обхода скоупа
   репозитория, которая давала удалённое выполнение кода через одну лишь prompt
   injection. Если твой сервер вообще не пишет/не исполняет команды — прекрасно, но
   это стоит явно задокументировать в описании инструментов, чтобы агент (и человек)
   видели границы.

2. **Tool poisoning / отравление метаданных.** Описания твоих MCP-инструментов — это
   тоже канал атаки: вредоносные инструкции, встроенные в метаданные инструмента,
   признаны самым распространённым уязвимым местом на стороне клиента. Практический
   риск: если кто-то сможет подменить или дополнить описание твоего tool (через issue,
   PR, форк, кэш), у агентов, которые тебя "спрашивают", можно тихо перехватить
   поведение. Проверь: подписаны ли релизы, нет ли возможности инжектить контент в то,
   что MCP отдаёт как "описание".

3. **Скрытые unicode-трюки.** Есть свежая находка про сокрытие вредоносной нагрузки
   в метаданных инструментов через unicode tag-блоки, что создаёт разрыв между тем,
   что видит человек при одобрении, и тем, что реально передаётся модели — актуально,
   если у тебя когда-нибудь появится форма для внешнего контента (гостевая книга,
   комментарии к decision log и т.п.), который потом просачивается в то, что отдаёт MCP.

4. **Reflected/stored injection через "живой" контент.** Похожий кейс уже был не с
   MCP-сайтом, а с базой данных: атакующий под видом обычного пользователя вставил
   вредоносную инструкцию в текст обращения в системе поддержки, подключённой к
   ИИ-агенту через MCP. Вывод для тебя: если где-то на сайте появится пользовательский
   ввод (даже "оставить отзыв"), он не должен попадать в то, что видит агент без
   санитайза.

5. **Открытость без аутентификации — это осознанный выбор, а не забытая настройка.**
   Внешние MCP-серверы без ограничений сами по себе считаются лишней поверхностью
   атаки для большинства случаев использования, поэтому раз ты сознательно делаешь его
   публичным (это часть концепции — "спрашивай агентом"), стоит хотя бы: rate limiting,
   логирование каждого вызова на уровне инфраструктуры (а не только в приложении —
   потому что скомпрометированный агент может влиять на собственные логи уровня
   приложения), и чёткий read-only режим по умолчанию.

## Практический чек-лист (можно прогнать самому за 20 минут)

- Все ли MCP-инструменты read-only? Если да — явно укажи это в system/tool description.
- Есть ли где-то на сайте точка, куда может писать посторонний (issue-форма,
  комментарии, webhook) и которая потом попадает в контент, отдаваемый через MCP?
- Есть ли rate limit / логирование на уровне сервера (не приложения) для
  MCP-эндпоинта?
- Не подписан ли билд так, что кто угодно через PR/форк может подменить tool description?
- Проверь CORS и заголовки на GitHub Pages — дефолтные настройки GH Pages обычно
  безопасны для статики, но если MCP-сервер живёт отдельно (не на GH Pages, а где-то
  с бэкендом) — там нужен отдельный аудит.

## Проверено по коду репозитория (добавлено 2026-08-14)

Что из чек-листа реально проверено в этом репозитории (не со слов источника):

- ✅ **Все 7 инструментов read-only.** `src/lib/mcp-tools.ts:165-346` — только чтение
  статичных JSON (`projects.json`, `principles.json`, `timeline.json`) + вычисления.
  Никаких записей, exec, файловых операций, сетевых вызовов к нефиксированным хостам.
- ✅ **SSRF-поверхность отсутствует.** Единственный исходящий fetch — захардкоженный
  URL dev.to (`mcp-tools.ts:228`: `https://dev.to/api/articles?username=mansio&per_page=8`).
  Ни один инструмент не принимает URL от вызывающего.
- ✅ **Единственная точка пользовательского ввода — `/chat`** (`worker/index.ts:200-222`),
  и она уходит в LLM (OpenRouter), а не в вывод MCP-инструментов. System prompt явно
  запрещает выдумывать и требует отвечать только данными инструментов
  (`worker/index.ts:87-94`).
- ⚠️ **Rate limiting НЕ реализован. Подтверждено экспериментом** (2026-08-14): бург 20 запросов с curl-UA → 200×20, 0×429. В `worker/index.ts` нет счётчиков/лимитов, в `wrangler.toml` нет Cloudflare rate limiting. Частичное смягчение есть на границе CF: бот-UA (`Python-urllib/3.x`) → 403 (bot-protection). Решение: CF Rate Limiting API (`[[ratelimits]]` binding, wrangler 4.36+, per-location, без дополнительной латентности) — см. KI-007.
- ⚠️ **Логирование вызовов уровня инфраструктуры отсутствует** (wrangler.toml не содержит настроек логирования; в коде воркера логирования нет). Workers Observability/Logs доступны на уровне CF без кода.
- ⚠️ **Аутентификации нет — осознанно.** `ALLOWED_ORIGINS` (`wrangler.toml:7-8`,
  `worker/index.ts:61-73`) ограничивает только CORS для браузеров; MCP-клиенты без
  Origin проходят всегда. Это дизайн-решение (публичный endpoint), но по п.5 чек-листа
  его стоит зафиксировать явно.
- ✅ **Tool description не инжектируемы.** Описания — статичные строки в `TOOLS`;
  внешний контент (dev.to-статьи) не попадает в `description`/`inputSchema`, только в
  тело результата `get_articles`.
- 🔴 **НОВОЕ (2026-08-14): `get_articles` падает на живом эндпоинте** — dev.to → 403
  с воркера (с обычного IP 200). Ки-006.
- ✅ **`readOnlyHint`-аннотация поддерживается SDK v2** — проверено tsc-экспериментом
  (EXPERIMENTS_LOG.md#4): `annotations: { readOnlyHint: true }` компилируется.
  Спецификация MCP 2026-07-28 вводит поле `annotations` у тулов.
